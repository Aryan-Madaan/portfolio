TDA, Tata Steel's enterprise AI assistant, is built by a team of six, which I lead. Across the frontend and backend we've made more than 5,200 commits, and the product now competes, feature for feature, with assistants built by companies a thousand times our size.

People assume the answer is long hours. It isn't. It's a planning method, run with the company's internal AI coding assistant.

## Write the bar before you build

Before we build a feature, we write down the bar it has to clear. Not a wish list: a line-by-line inventory of what the best products already do.

For a document canvas, for example, that meant listing every capability in ChatGPT's canvas, Microsoft's collaborative pages and Google Docs, from editing a selected passage to comments, versions, sharing and permissions, and marking which one sets the floor and which one sets the ceiling. That list is the bar. If we ship below the floor, users notice on day one.

## Check the plan against the real code

The second step is reading our own code honestly. Every plan records what TDA actually does today, checked against the code rather than the documentation, because documentation drifts and code doesn't lie.

The gap between the bar and the code is the feature.

## Split it into phases that each ship

Every plan ends in delivery phases, each of which is usable on its own, plus a written list of risks, assumptions and open questions that someone has to answer before building starts. Decisions get made in the plan, not halfway through the build.

## Where the AI coding assistant fits

This is the part that makes six people enough. The research, the competitive inventory and the first pass of reading the codebase are exactly the kind of exhaustive, careful work an AI coding assistant is good at and people are bad at sustaining. Every major feature now starts with a plan like this.

The judgement stays with us: what the bar should be, which gaps matter, what to defer and what never to build. The assistant does the legwork; we make the calls.

## What I'd tell another small team

- Write the bar before the code. It turns "is this good enough?" into a checklist.
- Trust the code over the docs when describing where you are today.
- Make every phase shippable, so a plan never becomes a six-month bet.
- Use AI for the exhaustive parts, and keep humans on the decisions.

Speed comes from not having to change your mind halfway through.
